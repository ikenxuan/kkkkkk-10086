# 多线程下载设计

## 目标

为插件统一的 `Networks.downloadStream()` 下载入口增加可选的 HTTP Range 分片并发下载能力，并通过锅巴面板配置。功能默认关闭，关闭时保持现有单线程下载行为和返回值不变。

## 配置

在 `upload` 配置中增加：

- `downloadMultiThread`: 布尔值，默认 `false`。
- `downloadConcurrency`: 数字值，默认 `4`，锅巴面板限制为 `2–8`。

运行时仍需独立校验和钳制配置值，不能只依赖锅巴组件限制。并发配置只控制单个文件的分片 worker 数量，不改变插件其他已有的并发行为。

锅巴面板将把两个字段放在现有下载限速设置旁边。配置类型文档和兼容 `app` 配置键同步更新，使 `upload.*` 和既有配置适配路径行为一致。

## 架构

保留 `downloadFile()` 和 `Networks.downloadStream()` 的调用方式及返回结构 `{ filepath, totalBytes }`。在 `downloadStream()` 内部根据以下条件选择实现：

1. `downloadMultiThread` 严格为 `true`。
2. 不是直播流。
3. 下载目标具有有限且可信的总大小，并达到内部的最小文件大小阈值。
4. Range 探测请求返回 `206`，`Content-Range` 格式有效且总大小正确。
5. 后续分片请求能够保持稳定的资源身份。

不满足任一条件时，直接调用现有单线程下载逻辑。多线程是增强路径，不会改变未知大小、直播流、服务器不支持 Range 或服务器忽略 Range 时的既有行为。

### 分片流程

1. 使用 `Range: bytes=0-0` 探测响应，解析总大小、最终 URL 和可用的强 `ETag` 或 `Last-Modified`。
2. 按总大小和并发数划分连续、互不重叠的闭区间 `[start, end]`。
3. 在最终文件同目录创建带唯一标识的 staging 文件，预分配为总大小；不直接写入最终文件。
4. 以受限 worker 数并发请求各分片，每个 worker 只写入自己负责的偏移区间。
5. 每个分片独立重试，不因单个分片失败而重新下载已成功的分片。
6. 全部完成后校验 staging 文件大小和各分片确认状态。
7. 关闭文件句柄后，将 staging 文件原子替换为最终文件。
8. 成功或失败都清理当前下载拥有的 staging 文件和计时器。

分片请求合并调用方 headers 后由下载器强制设置 Range、`Accept-Encoding: identity` 和流式响应选项，避免调用方 headers 覆盖分片范围或引入透明解压。

## 稳定性与错误处理

### 响应校验

每个分片必须满足：

- HTTP 状态为 `206`。
- `Content-Range` 的起止位置与请求区间完全相同。
- `Content-Range` 总大小与初始探测一致。
- 收到的字节数等于 `end - start + 1`。
- 响应没有改变资源校验器；优先校验强 `ETag`，没有时使用 `Last-Modified`。

状态码为 `200`、Range 响应格式错误、返回长度不符、资源校验器变化或不可恢复的 HTTP 错误，都不会被当作分片成功。能力探测阶段出现这些情况时回退单线程；并发阶段出现资源不一致或结构性错误时取消其他 worker，删除 staging 文件并抛出错误，避免生成混合文件。

### 重试

沿用现有下载的最大重试次数和错误分类原则，但重试粒度改为单个分片。连接重置、超时、指定的 `5xx` 和可重试限流状态可按现有策略退避重试；持久 `4xx`、校验器变化和格式错误终止本次多线程下载。终止错误通过共享 `AbortController` 取消其他请求，所有流和文件句柄在 `finally` 中关闭。

### 限速与进度

现有 `downloadMaxSpeed` 作为单个文件的共享总限速，不对每个分片重复套用。多线程下载的进度按各分片已确认写入的字节数聚合，并避免重试字节重复计数；保持现有进度回调形态和节流频率。

### 文件发布与清理

staging 文件必须和最终文件处于同一目录，使用唯一的下载标识避免并发调用冲突。成功前不暴露最终文件的新内容；全部校验通过且句柄关闭后才执行原子替换。失败时只删除本次创建的 staging 文件，不删除或截断已有最终文件。直播流继续使用现有直接写入和大小限制语义。

## 测试设计

使用 Node 内置 `node:test` 和 `node:http` 建立本地 Range fixture，不新增测试依赖。测试至少覆盖：

1. 多个分片乱序返回仍能正确组装原始内容。
2. 并发 worker 数不超过配置值。
3. 服务端忽略 Range 返回 `200` 时自动回退单线程。
4. 未知大小或直播流不进入多线程路径。
5. `Content-Range` 起止位置、总大小和实际字节数不匹配时失败并清理 staging。
6. 单个分片连接失败只重试该分片，最终可成功完成。
7. `ETag` 或总大小变化会取消任务并拒绝发布混合文件。
8. 最终路径在成功前不会出现新的 staging 内容，成功后内容完整。
9. 已存在的最终文件在并发失败时保持不变。
10. 共享限速不会按 worker 数倍增。
11. 所有请求、句柄和定时器在成功、失败、取消路径都能释放。
12. 默认关闭时现有单线程行为不变。

## 非目标

- 不改造 `ImageHelper` 当前的完整缓冲图片下载。
- 不改变 Bilibili 视频和音频两个独立文件的上层并发逻辑。
- 不为直播流强行引入 Range 分片。
- 不让多线程配置影响其他 HTTP 请求或全局连接池策略。
- 不引入新的第三方并发、重试或限速依赖。
